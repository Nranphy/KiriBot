# KiriBot 目录结构

## 文档定位

本文约定项目的规划目录结构与职责。按功能实施进度创建目录，不提前生成大量空文件；目录树不代表对应功能已经实现。

## 放置规则

Manager 的 Python 应用代码直接按层放在 `src/kiribot/`，不再嵌套 `manager/`；本文中的 `controller/`、`services/`、`clients/`、`models/`、`infra/` 均相对此应用包。NoneBot2 Worker 模板的 Python 应用代码放在 `workers/nonebot2/src/`。各独立项目的根目录不放 Python 启动脚本或业务代码。各 Python 子包包含 `__init__.py`，目录树省略重复项。

根目录的 `Dockerfile` 用于部署 Manager，不默认包含所有 Worker 的运行环境。Worker 按实例配置独立启动，模板维护自身依赖与运行说明；是否与 Manager 放在同一容器、WebUI 的交付方式和持久化目录在部署实现时明确。根目录的 `pyproject.toml`、`uv.lock` 管理 Manager 环境，NoneBot2 模板使用自身的依赖声明与锁文件。

`controller/` 包含 FastAPI 管理接口及 NoneBot2 管理机器人入口，作为同一管控层调用管理服务。Controller 注册现成平台 Adapter，提供 Manager Bot 专用反向端点，不要求独立进程。

Manager 按 `controller/`、`services/`、`clients/`、`models/` 横向分层，各层内部再按领域或能力组织；`services/` 下每个领域使用独立子包，领域相关的服务与辅助实现放在该子包内，不在 Manager 顶层为每个领域创建包含各层的目录。

调用关系为 `controller → services → clients`。Service 实现用户、权限、Gateway、实例、数据、插件及迭代的业务规则；Client 封装数据库、进程和网络等底层访问，可被多个 Service 复用，不要求与领域一一对应。Service 可以调用其他 Service；没有实际职责时，不创建空壳层或文件。

Gateway 的配置读取和整体生命周期由 `services/gateway/service.py` 中的 `GatewayService` 协调，`registry.py` 使用 `ConnectionKey` 和 `SubscriberKey` 维护带协议类型的外部会话与内部订阅者。`OneBot11Gateway` 独立管理 OneBot 11 外部接入、内部会话和 Action 路由；`SatoriGateway` 独立管理 Satori 主动连接、心跳、内部事件服务及 HTTP API 代理。协议会话与网络访问实现保留在各自的 Gateway 子包内，不在顶层 `clients/` 重复提供 OneBot 或 Satori Client。`transport.py` 只复用 JSON WebSocket 传输，Router 只处理协议消息分发。Controller 只注册端点、提取请求并转换代理响应。Manager 和 Worker 都作为普通内部客户端连接 Gateway。

OneBot v11 反向连接由 `/gateway/external/{connection_name}/onebot/v11/ws` 接收，正向连接由 Gateway 按配置主动连接外部 Universal WebSocket；两种模式共用 Router 和内部端点。内部 OneBot 使用 `/gateway/internal/{client_id}/{connection_name}/onebot/v11/ws`；内部 Satori 使用 `/gateway/internal/{client_id}/{connection_name}/satori` 服务根地址。Satori 标准模式由应用主动连接 SDK，当前不实现 WebHook。

`models/gateway.py` 使用判别联合定义 OneBot 正向、OneBot 反向和 Satori 正向配置，不能组合无意义的协议字段；OneBot 配置必须显式填写 `mode`，缺失时拒绝启动。Settings 指定配置路径，默认 `config/gateway.json`，不存在时使用空配置且不创建文件。应用根据登记配置为 Manager 的 NoneBot Adapter 生成普通内部客户端地址；外部断开时对应 Manager 和 Worker 连接一并关闭并由 Adapter 重连。

`controller/admin/` 按领域拆分文件，同一领域的 Web 接口和 Bot 管理命令放在同一个文件中，调用相同的管理服务。例如 `health.py` 维护 Web 健康接口与 Bot `/health` 管理命令，实例管理实现时放在 `instances.py`。按实际需求提供入口，不要求每个领域同时实现 Web 和 Bot 两种入口。入口注册统一由应用初始化流程装配。Manager 不加载外部业务插件，机器人管理命令作为自身 Controller 实现。

`services/plugins/` 负责 Worker 插件安装与配置管理的业务流程，`workers/nonebot2/src/kiribot_worker/plugins/` 存放 NoneBot2 模板的自有业务插件。其他实现按其生态组织插件；市场插件的安装与兼容检查须针对实例的实现及运行环境。

`models/` 存放内部业务输入输出模型。HTTP 请求响应结构放在 Controller 的对应 `admin/` 或 `internal/` 范围内，持久化记录等底层模型保留在 Client 范围内；需要进一步拆分时按实际规模组织。

Manager 通过 `controller/internal/` 的 HTTP 接口向 Worker 提供数据库、渲染、网络请求、AI 和权限判断等公共能力；接口调用路径为 `controller → services → clients`。Worker 的调用封装保留在自身项目中，不通过导入 Manager 的 Python 模块获取公共能力。机器人通信使用 OneBot、Satori，不设独立 `protocol/` 目录；HTTP 接口契约由对应入口维护。`infra/` 承载配置加载、日志初始化等应用运行基础设施；数据库、进程和外部服务访问仍由 `clients/` 封装，业务规则与模型保留在对应层，不作为跨程序共享代码或业务杂项目录。

`workers/` 维护可用于创建实例的模板，按机器人实现命名，如 `nonebot2`；后续确需维护 Koishi 模板时再增加 `koishi/`，不按编程语言分类。当前仅规划 NoneBot2 模板，不提前创建其他实现目录。

模板与运行实例分开。实例的名字、实现或模板来源、工作目录、允许 AI 修改的目录、启动方式及支持的协议由 Manager 配置管理。实例工作目录不默认等于仓库模板目录；运行数据、安装的依赖和实例配置不回写模板。实例目录位置及模板生成实例的具体方式待实现时确定。

允许 AI 修改的目录是实例配置中的独立范围，不能从工作目录推导为整个目录均可修改。Manager 在开发与调试流程中按该范围约束文件修改；具体路径校验与隔离方式另行设计。

`webui/` 存放管理界面源码，`migrations/` 存放数据库迁移，根目录 `tests/` 验证 Manager 与跨程序集成行为，各 Worker 模板在自身 `tests/` 或其生态对应目录中维护测试。

新增、删除或调整目录时，同步更新本文；具体模块内部结构按实际职责逐步细化。
