# KiriBot 总体架构

## 1. 文档定位

本文记录 KiriBot 的目标架构、职责边界与主要流程，不规定代码目录结构。所有能力均为设计目标，具体实现和首版交付范围以后续文档及代码为准。

## 2. 运行模型

Manager 是长期运行的主程序，Worker 是独立运行的机器人进程。Gateway 是 Manager 管理的通信能力；是否需要独立部署为进程尚未确定。

消息路径：外部组件 ↔ Gateway ↔ Worker ↔ 插件。

管理路径：WebUI / 管理员机器人指令 → Manager 管理服务 → Worker / 配置 / 插件 / 用户 / 权限。

MVP 只管理一个 Worker。Gateway 仍按明确的实例标识路由，但不提前建设多实例调度或集群管理。

## 3. Manager 职责

| 能力 | 职责 |
| --- | --- |
| 实例管理 | 启动、关闭、重启 Worker，修改配置、环境变量和插件启用状态 |
| 用户管理 | 根据 Gateway 收到的事件维护用户标识、所属平台等信息 |
| 数据库 | 提供统一的数据服务，并通过工具组向插件开放数据库访问能力 |
| 工具组 | 提供数据库访问、HTML 图片渲染、网络请求、AI 接入和鉴权 Depend 等常用能力 |
| 机器人迭代 | 管理触发、开发、调试、审批和部署流程 |
| Gateway | 对接外部组件，接收 Worker 连接，并路由双向通信 |
| 权限管理 | 基于用户信息判断管理操作和插件功能的访问权限 |
| 管理入口 | 为 WebUI 和管理员机器人指令提供一致的管理能力 |
| 市场插件管理 | 负责市场插件的接入及相关依赖与配置变更 |

Manager 维护管理状态和配置的权威来源，Worker 执行已生效的配置。配置、环境变量或插件状态修改如何生效、是否需要重启，应由具体实现明确说明，不默认具备热更新能力。

## 4. Gateway 职责

Gateway 对接 OneBot 和 Satori 两套协议的外部组件，同时接受 Worker 连接。接收到的事件路由到对应机器人实例；Worker 发起的平台操作及响应经 Gateway 返回外部组件。

用户信息维护路径：外部事件 → Gateway 提取身份上下文 → Manager 用户管理 → Worker 处理事件。

事件上下文需要保留平台用户身份、机器人身份及必要的会话信息。不同平台的相同用户标识不能直接视为同一用户；跨平台账号关联规则另行设计。

Gateway 负责连接与路由，不执行具体插件业务。协议版本、传输方式、内部事件格式、请求关联、重连以及 Worker 不可用时的事件处理策略尚待确定。不预设不同协议的能力完全一致。

## 5. Worker 与插件

Worker 负责具体机器人功能和插件执行，连接 Gateway 获取事件并发起平台操作。实例生命周期和管理配置由 Manager 控制。

插件是功能开发与迭代的基本单位。自有插件需要高度规范，以便 AI 开发和调试，规范至少覆盖命令解析、权限 Depend、数据库访问、配置声明、生命周期及验证方式。

插件调用路径：事件 → Worker 插件入口 → Alconna 命令解析 / 权限 Depend → 业务逻辑 → 工具组 → 结果输出。非命令事件按实际入口处理，不要求所有插件事件经过命令解析。

工具组是插件访问公共能力的统一入口。Manager 提供对应服务，Worker 侧如何封装调用、哪些能力在本地执行及如何跨进程通信，需在工具契约中确定。

自有插件和市场插件分别管理：自有插件遵循 KiriBot 的开发契约；市场插件可能使用自身接口，不能假设其天然符合自有插件规范。接入时由 Manager 检查其依赖、配置及与当前运行环境的兼容性。

市场插件接入路径：管理入口 → Manager 接入与配置 → Worker 加载并验证。Worker 插件不自行执行市场安装和管理环境变更。

## 6. 用户与权限

Manager 基于用户身份维护权限规则。WebUI 与机器人管理指令调用同一组管理服务，并在可信管理边界进行权限校验，不能只依赖界面隐藏或 Worker 命令入口的检查。

插件权限通过统一的鉴权 Depend 接入。管理权限与普通插件功能权限应有明确边界；角色、权限粒度、管理员初始化和身份绑定方式仍待设计。

机器人管理指令依赖 Worker 正常运行。因此 WebUI 是独立于机器人指令的管理入口，Worker 停止或异常时仍需能够通过它执行启动和恢复操作。

## 7. 数据与工具组

Manager 统一提供数据库服务，工具组面向插件提供受控访问入口。管理数据与插件业务数据的模型、命名空间、迁移和访问边界应分别明确，不能因共享数据库服务而默认共享全部数据。

数据库、渲染、网络和 AI 能力应有明确的输入输出、异常、资源生命周期与配置来源。管理凭据和第三方服务密钥不进入普通事件或用户可见输出。具体库、引擎和部署方式暂不指定。

## 8. 机器人代码迭代

迭代路径：触发 → 开发 → 调试 → 审批 → 部署。

| 阶段 | 目标 |
| --- | --- |
| 触发 | 记录需求、目标实例与插件范围 |
| 开发 | 基于插件规范完成代码、配置及必要的数据变更 |
| 调试 | 验证插件行为和集成结果，形成可审查的候选版本 |
| 审批 | 由具备相应权限的主体确认候选版本和部署内容 |
| 部署 | 将已审批版本应用到目标 Worker，并确认运行结果 |

调试不应直接替换正在运行的正式版本。审批应绑定确定的候选版本；审批后代码或配置发生变化时，需重新验证与审批，不能部署未经审批的新内容。

AI 参与开发和调试，不因开发完成自动获得部署权限。迭代产物的版本管理、调试隔离、审批记录、部署失败恢复及回滚机制需在实现迭代能力前补充专题设计。

## 9. MVP 与待定事项

已确定的 MVP 限制是单 Worker 实例。Manager、Gateway 与 Worker 保持职责分离，但不要求为每种逻辑能力创建独立服务。

实施前需要进一步确定：进程连接与认证、OneBot 和 Satori 的目标版本、内部通信契约、数据库和工具接口、插件规范、配置生效机制、权限模型，以及代码迭代的隔离与恢复方式。

这些待定事项不影响本文作为总体设计入口；涉及具体实现时，应补充明确约定，不由 Agent 默认为已定方案。
