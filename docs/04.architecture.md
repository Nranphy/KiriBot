# KiriBot 总体架构

## 1. 文档定位

本文记录 KiriBot 的目标架构、职责边界与主要流程，代码放置约定见 [目录结构](05.directory-structure.md)。所有能力均为设计目标，具体实现和首版交付范围以后续文档及代码为准。

## 2. 运行模型

Manager 是长期运行的主程序，内部包含 Controller 管控层、Gateway 通信层及管理服务。Worker 是独立运行的机器人进程。Controller 是逻辑职责划分，不要求独立进程；Gateway 是否需要独立部署为进程尚未确定。

消息路径：外部组件 ↔ Gateway ↔ Controller 的 NoneBot2 Adapter / Worker 的协议客户端 ↔ 管理插件 / 业务插件。

管理路径：WebUI → Controller FastAPI / 管理员机器人指令 → Controller NoneBot2 → Manager 管理服务 → Worker / 配置 / 插件 / 用户 / 权限。

工具调用路径：Worker → Manager 内部 HTTP 接口 → Service → Client。该路径独立于 Gateway 的机器人协议转发。

MVP 只管理一个 Worker。Gateway 仍按明确的实例标识路由，但不提前建设多实例调度或集群管理。

## 3. Manager 职责

Manager 按 Controller、Service、Client 横向分层，内部业务模型统一放在 Models 层。Controller 提供管理入口，Service 实现业务规则与流程，Client 封装数据库、进程及网络访问。各层内部按领域或能力组织，具体目录见 [目录结构](05.directory-structure.md)。

管理调用路径：Controller → Service → Client。Service 可调用其他 Service；Gateway 的持续通信由 Service 管理生命周期、Client 执行协议收发，无需逐条经过 Controller。

| 能力 | 职责 |
| --- | --- |
| 实例管理 | 启动、关闭、重启 Worker，配置实例名字、工作目录、允许 AI 修改的目录、启动方式、支持的协议、环境变量和插件启用状态 |
| 用户管理 | 根据 Gateway 收到的事件维护用户标识、所属平台等信息 |
| 数据库 | 提供统一的数据服务，并通过工具组向插件开放数据库访问能力 |
| 工具组 | 提供数据库访问、HTML 图片渲染、网络请求、AI 接入和权限判断等常用能力 |
| 机器人迭代 | 管理触发、开发、调试、审批和部署流程 |
| Gateway | 对接外部组件，接收 Controller 和 Worker 连接，并路由双向通信 |
| 权限管理 | 基于用户信息判断管理操作和插件功能的访问权限 |
| Controller | 通过 FastAPI 为 WebUI 提供接口，通过 NoneBot2 管理插件处理管理员机器人指令 |
| 市场插件管理 | 负责市场插件的接入及相关依赖与配置变更 |

Manager 维护管理状态和配置的权威来源，Worker 执行已生效的配置。配置、环境变量或插件状态修改如何生效、是否需要重启，应由具体实现明确说明，不默认具备热更新能力。

## 4. Gateway 职责

Gateway 对接 OneBot 和 Satori 两套协议的外部组件，同时接受 Controller 和 Worker 作为客户端连接。内部机器人通信继续使用对应的 OneBot 或 Satori 协议，不另行设计统一的平台事件协议。

不设独立的 `protocol/` 目录。数据库、AI 等公共能力通过 Manager 内部 HTTP 接口提供，接口模型归 Controller 对应入口维护。

Gateway 实现所选协议模式中连接、鉴权、存活及转发所需的最小能力。事件、平台 API 请求和响应尽量保留原始协议内容，按连接与路由规则双向转发；不重新实现 NoneBot2 Adapter 的事件模型和插件处理能力。

Controller 安装 NoneBot2 及所需的现成 OneBot、Satori Adapter；Worker 使用其实现支持的协议客户端，通过 Gateway 使用机器人账号。Worker 按实例声明支持 OneBot 或 Satori，不要求支持两种协议，也不要求使用 NoneBot2。两者可以使用同一账号，但属于不同内部客户端。Gateway 需区分账号身份与客户端身份，关联 API 请求和响应，避免响应误投；必要的关联标识映射在协议转发设计中确定。

管理事件与业务事件的分发规则尚待确定。需要明确哪些事件仅交给 Controller、哪些交给 Worker、哪些共同接收，并避免同一账号重复回复。不将这些规则默认为全部广播或仅按账号单播。

用户信息维护路径：外部事件 → Gateway 提取必要身份上下文 → Manager 用户管理；原始事件按路由规则转发给 Controller / Worker。

事件上下文需要保留平台用户身份、机器人身份及必要的会话信息。不同平台的相同用户标识不能直接视为同一用户；跨平台账号关联规则另行设计。

Gateway 负责连接与路由，不执行具体插件业务。协议版本、传输模式、握手与心跳、请求关联、重连以及客户端不可用时的事件处理策略尚待确定。不预设不同协议的能力完全一致或所有传输模式均可直接代理。

### Controller 管控层

Controller 同时提供 FastAPI 和 NoneBot2 两种入口。FastAPI 面向 WebUI，NoneBot2 注册现成 Adapter、连接 Gateway，并加载管理员机器人指令插件。两种入口调用相同管理服务，共用用户、权限和实例管理规则。

Controller 的应用入口负责 FastAPI、NoneBot2 及相关资源的初始化和生命周期装配。具体 Driver 选择与服务运行方式在实现时确定，不要求分别启动两套管理服务。

## 5. Worker 与插件

Worker 是语言和框架不限的独立程序，负责具体机器人功能和插件执行，作为 Gateway 客户端获取事件并发起平台操作。实例生命周期和管理配置由 Manager 控制，管理指令插件由 Controller 承担。

本仓库按机器人实现维护 Worker 模板，当前仅规划 `nonebot2`，后续可增加 `koishi` 等模板。NoneBot2 模板采用 NoneBot2、现成 Adapter 和 Alconna；其他实现遵循自身生态，不强制采用 NoneBot 插件契约。

模板是创建与迭代实例的源码基础，不等同于运行实例。Manager 为实例维护稳定标识、名字、实现或模板来源、工作目录、允许 AI 修改的目录、启动方式、支持的协议和连接配置。名字用于展示，实例标识用于路由与关联；字段格式、启动方式和配置存储形式待实现时明确。

工作目录用于程序启动和运行，允许 AI 修改的目录限定开发与调试的文件修改范围，两者独立配置。不能默认 AI 可修改整个工作目录或直接修改仓库模板；路径校验与隔离机制需在迭代实现前确定。

插件是功能开发与迭代的基本单位。自有插件需要高度规范，以便 AI 开发和调试，规范至少覆盖本实现的命令解析、Manager HTTP 权限与数据接口接入、配置声明、生命周期及验证方式。

插件调用路径：事件 → Worker 插件入口 → 本实现的命令解析 / 权限接入 → 业务逻辑 → Manager 内部 HTTP 接口 → 结果输出。非命令事件按实际入口处理，不要求所有插件事件经过命令解析。

Manager 通过内部 HTTP 接口向 Worker 提供公共能力，原生支持跨语言调用。Worker 可按自身语言封装客户端，不依赖 Manager 的 Python 包；命令解析与框架适配在 Worker 本地完成。HTTP 路径、请求响应、错误与认证的具体契约需另行确定。

自有插件和市场插件分别管理：自有插件遵循 KiriBot 的开发契约；市场插件可能使用自身接口，不能假设其天然符合自有插件规范。接入时由 Manager 检查其依赖、配置及与目标 Worker 实现及运行环境的兼容性。

市场插件接入路径：管理入口 → Manager 接入与配置 → Worker 加载并验证。Worker 插件不自行执行市场安装和管理环境变更。

## 6. 用户与权限

Manager 基于用户身份维护权限规则。Controller 的 FastAPI 接口与机器人管理指令调用同一组管理服务，并在可信管理边界进行权限校验，不能只依赖界面隐藏或命令入口的检查。

插件权限通过 Manager 内部 HTTP 接口接入，NoneBot2 模板可提供鉴权 Depend 封装。受保护的公共能力还需在 Manager 可信边界校验权限；Worker 实例身份与平台用户身份应分别校验，不能仅凭 Worker 提交的用户标识授予管理权限。管理权限与普通插件功能权限应有明确边界；角色、权限粒度、管理员初始化和身份绑定方式仍待设计。

机器人管理指令由 Controller 执行，不依赖 Worker 正常运行。Worker 停止或异常时，只要 Manager、Controller、Gateway 与外部连接正常，管理员仍可通过机器人指令启动或恢复 Worker。WebUI 提供另一种管控入口。

## 7. 数据与工具组

Manager 统一提供数据库服务，通过内部 HTTP 接口面向 Worker 提供受控访问入口。管理数据与插件业务数据的模型、命名空间、迁移和访问边界应分别明确，不能因共享数据库服务而默认共享全部数据。

数据库、渲染、网络和 AI 能力应有明确的输入输出、异常、资源生命周期与配置来源。管理凭据和第三方服务密钥不进入普通事件或用户可见输出。内部 HTTP 接口沿用动作式 POST 约定，基本结构使用语言无关的 JSON，不暴露 Python 对象或框架依赖；二进制产物的交付方式另行确定。接口需明确 Worker 实例认证与能力授权。具体库、引擎和部署方式暂不指定。

## 8. 机器人代码迭代

迭代路径：触发 → 开发 → 调试 → 审批 → 部署。

| 阶段 | 目标 |
| --- | --- |
| 触发 | 记录需求、目标实例与插件范围 |
| 开发 | 基于插件规范完成代码、配置及必要的数据变更 |
| 调试 | 验证插件行为和集成结果，形成可审查的候选版本 |
| 审批 | 由具备相应权限的主体确认候选版本和部署内容 |
| 部署 | 将已审批版本应用到目标 Worker，并确认运行结果 |

调试不应直接替换正在运行的正式版本。审批应绑定确定的候选版本；审批后代码或配置发生变化时，需重新验证与审批，不能部署未经审批的新内容。

AI 参与开发和调试，不因开发完成自动获得部署权限。迭代产物的版本管理、调试隔离、审批记录、部署失败恢复及回滚机制需在实现迭代能力前补充专题设计。

## 9. MVP 与待定事项

已确定的 MVP 限制是单 Worker 实例。Manager、Gateway 与 Worker 保持职责分离，但不要求为每种逻辑能力创建独立服务。

实施前需要进一步确定：进程连接与认证、OneBot 和 Satori 的目标版本、内部 HTTP 接口契约与认证、数据库和工具接口、插件规范、配置生效机制、权限模型，以及代码迭代的隔离与恢复方式。

这些待定事项不影响本文作为总体设计入口；涉及具体实现时，应补充明确约定，不由 Agent 默认为已定方案。
