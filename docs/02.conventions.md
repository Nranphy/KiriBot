# KiriBot 代码与文档规范

## 1. 文档定位

本文规定 KiriBot 中开发者和 AI Agent 的代码与文档生成风格。Python 专项约定见 [Python 代码风格](03.python-style.md)，具体框架细则由后续实际实现及模块文档补充。

## 2. 代码生成

修改前优先参考同一目录、同一模块或相邻文件，沿用现有文件组织、命名、类型定义、错误处理、注释、测试和工具使用方式。新代码应与已有实现保持一致。

优先复用现有工具函数、组件、类型和服务。新增抽象应解决当前实际存在的问题，不为尚未出现的需求创建通用框架、配置层或扩展机制。

生成代码应实现当前需求的完整行为，不以占位实现、伪造数据或吞掉异常来表现功能已完成。必要的错误处理应清楚表达失败原因，并遵循所在模块的约定。

当用户没有要求重构时，控制修改范围，不顺带重命名、格式化或调整无关代码。发现相关问题时，说明实际影响；超出本次范围的改进单独提出。

除非当前需求确实需要，或用户明确要求，不修改依赖声明与锁文件。需要调整依赖时，优先使用项目采用的 CLI 工具；工具不可用或项目要求手动维护时，才直接编辑，并说明原因。

项目使用 Python。尚无既定实现时，选择满足当前需求的简单方案，记录影响后续开发的重要约定，具体框架与工具根据当前需求确定。

## 3. 注释与命名

代码标识符使用对应语言和生态惯用的英文命名，保持业务术语一致，避免无意义缩写。

关键函数、类和模块应按所在语言的惯用方式编写文档注释或文档字符串，说明职责、边界、重要约束，以及不容易从实现中看出的原因。

无语言、框架或协议特殊要求时，注释和文档字符串使用中文。参数、返回值等结构化标记遵循工具的通行写法，不强行翻译。

标题或概括性质的单行文本末尾不加句号；完整句子和多行说明使用正常标点。

注释应服务于长期维护，不记录本次任务、修改过程或临时对话背景，不重复代码已经清楚表达的内容。不要为每一行实现机械添加注释。

## 4. 文档风格与维护

文档默认使用中文，先说明用途或结论，再解释必要的背景、规则和例子。使用准确、直接的措辞，避免空泛宣传、重复总结和没有依据的判断。

区分当前实现、已确认设计和待定事项。示例应标明用途；命令必须与实际工具一致，不能将未执行的操作描述为已验证。

处理任务前，查阅修改目录及其父级的相关 `README.md` 和 `docs/`。普通项目文档存在差异时，优先遵循最接近当前修改位置的文档。

职责分工如下：

- `README.md` 提供项目入口及实际可用的使用说明。
- `AGENTS.md` 提供 Agent 工作入口、阅读顺序和关键约束。
- `docs/` 记录背景、约定、设计与实现细节，避免将同一规则复制到多个文件。

行为、接口、配置或开发方式变化时，同步更新对应文档。调整目录结构时，更新已经存在的目录职责或结构说明；不要求为尚未形成的架构提前建立目录树。

用户要求与文档不同，应说明差异并优先执行用户的明确要求。若需要将差异固化为长期规范，再确认其适用范围，不自行扩大一次性需求。

## 5. 接口风格

以下约定仅适用于后续确实引入的 HTTP API，不要求当前创建接口或服务。

内部接口采用 `POST`，以业务动作组织路径和请求体；开放接口采用 REST 风格，以资源和 HTTP 方法表达查询、创建、更新与删除。具体模块或第三方协议已有约定时，遵循其约定。

接口错误使用符合语义的 HTTP 状态码，不以始终返回 `200` 的方式包装失败。错误响应可包含必要的错误码、说明和请求追踪信息，不暴露密钥或内部敏感信息。

非 HTTP 的消息协议、SDK 和函数接口应使用自身的类型、错误和兼容约定，不机械套用 HTTP 规则。

## 6. 验证与交付

根据修改影响选择验证方式。行为变更应验证关键成功路径、失败路径和受影响边界；优先运行现有相关检查，不编写仅重复实现、没有验证价值的测试。

纯文档修改检查内容一致性、相对链接和差异格式，无需为此引入测试框架。项目尚未配置的检查工具，不描述为已经通过。

交付说明默认使用中文，先说实际完成了什么，再说明验证结果。涉及依赖变化、兼容影响或未完成事项时，补充具体原因和影响。

未执行或无法执行的必要检查应明确说明原因。区分已完成、已验证和待处理，不将预期结果表述为实际结果。

## 7. Git 规范

提交信息遵循 Conventional Commits：

```text
<type>(<scope>): <summary>
```

`type` 使用英文小写，常用 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`build` 和 `ci`。

`scope` 可选，使用实际模块的简短英文名。单模块修改优先填写，多模块可用半角逗号分隔，全局修改可省略；不预设尚不存在的模块名。

`summary` 使用中文，以动词开头，描述最终修改结果，末尾不加句号。例如：

```text
docs: 添加模型开发与文档规范
```

每个提交围绕一个明确目的，可包含直接相关的代码、测试、配置和文档。避免混入无关重构或格式化，也不机械拆开无法独立成立的修改。

提交前检查实际 diff 和暂存区，排除凭证、本地环境文件、缓存、构建产物、调试代码及无关修改，并完成适用于本次变更的检查。

共享历史不随意改写。强制推送、变基共享分支、删除分支或丢弃未提交修改，需要明确的用户授权；已有授权按其范围执行。
