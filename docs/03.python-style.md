# KiriBot Python 代码风格

## 1. 文档定位

本文规定本项目 Python 代码的生成与维护风格，不预设目录结构或业务架构。

Python 版本、格式化、静态检查和测试选项以实际 `pyproject.toml` 及工具配置为准。修改已有代码时，优先沿用同目录、同模块的实现；发现与本文不一致的约定时，说明差异，不顺带重排无关代码。

## 2. 基本原则与命名

代码应清晰、直接、类型明确。函数和类保持职责集中，优先复用已有实现，不为假设中的扩展提前引入复杂抽象。

- 模块、文件、函数、方法和变量使用 `snake_case`。
- 类和数据模型使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 命名表达业务含义，避免缩写，以及缺乏上下文的 `data`、`obj`、`manager`、`helper` 等宽泛名称。

不因本文提及某个工具或库就自动添加依赖。依赖变更遵循通用规范，优先通过项目实际使用的 CLI 完成。

## 3. 类型标注

新增函数、方法和类属性应尽量提供类型标注。公共函数、服务方法、数据访问方法、外部客户端方法及接口处理函数必须明确参数类型和返回类型。

在项目 Python 版本支持时，优先使用内置泛型，例如 `list[str]`，可选值使用 `str | None`。类型语法应与项目支持的最低版本兼容。

避免用 `Any` 替代已经明确的数据契约。单模块使用的类型保留在该模块内；只有表达同一个稳定概念并确实跨模块复用时，才提取共享类型。

## 4. 导入与初始化

导入按以下顺序分组，组间留空行：

1. 标准库
2. 第三方库
3. 项目内部模块

使用明确导入，不使用通配符。普通 Python 包使用 `__init__.py` 提供清晰的包边界；其内容保持轻量，必要时导出稳定入口，不承载复杂业务逻辑。

避免在导入时连接外部服务、启动任务或修改全局应用实例。资源创建、路由注册、处理器注册和关闭应在明确的初始化及生命周期入口中完成。

## 5. 异步代码与资源生命周期

异步运行环境中的数据库、HTTP 和其他 I/O 优先使用异步接口，使用 `async def` 并显式 `await`。同步入口不为了形式统一而强行改为异步。

不要在异步流程中直接执行长时间阻塞操作。必要的阻塞工作使用合适的线程执行器、任务队列或独立运行环境，不阻塞事件循环。

连接、会话、文件和任务应有明确生命周期，优先使用上下文管理器或框架生命周期机制完成释放。外部调用应根据实际场景配置超时，不让失败无限等待。

## 6. 职责与调用边界

Manager 遵循 `controller → services → clients` 的横向分层，内部业务模型放在 `models/`，各层内部按领域或能力拆分。具体放置方式见 [目录结构](05.directory-structure.md)。按实际复杂度实现各层，不为简单功能机械创建空壳或多层转发；Worker 与工具模块按各自职责组织。

接口、消息或事件处理入口负责接收与校验输入、获取调用上下文、调用业务逻辑和转换结果。复杂业务流程不堆积在入口函数中。

业务服务负责业务规则与流程，数据访问封装负责持久化，外部客户端负责第三方 API 或基础设施访问。避免在业务流程中散落 SDK、SQL 和 HTTP 调用细节。

需要协调多个业务模块时，可以用明确的应用用例组织编排；底层访问仍通过现有数据访问或客户端封装完成。不要仅为满足命名而创建空壳 Service、Repository 或 Client。

若引入 Web 框架，路由、中间件和异常处理器集中从应用创建入口注册，注册顺序明确，不依赖模块导入副作用。

## 7. 数据模型

外部请求与响应、内部业务输入输出及持久化记录具有不同契约，不应把同一个模型不加区分地传遍所有层级。

需要运行时校验的结构化数据优先考虑 Pydantic；已经采用该库时沿用其模型风格。简单内部数据结构可使用 `dataclass` 等标准库能力，不为形式统一新增依赖。

模型放在对应职责所属模块中，服务本体专注流程编排，不在服务文件中定义跨文件复用的数据模型。数据库表、ORM 和持久化记录保留在数据访问边界内，不直接作为外部响应传播。

命名表达场景，例如 `CreateTaskRequest`、`CreateTaskResponse`、`CreateTaskCommand`、`CreateTaskResult`、`TaskTable` 和 `TaskRecord`。这些是命名示例，不要求当前实现任务模块。

不要因为字段相似就提取共享模型，也不要为没有区别的内部调用机械复制模型。需要区分契约时，在对应边界显式转换。

## 8. 异常、事务与权限

使用表达具体业务含义的异常，不只抛出模糊的 `Exception`，不捕获后静默忽略。跨模块通用异常和单领域业务异常分别放在适合其复用范围的位置。

业务代码不直接返回 HTTP 响应。入口或公共异常处理逻辑负责将失败转换为对外错误。

涉及多个持久化操作的原子流程，应有明确事务边界。数据访问方法不擅自提交上层事务，也不通过相互调用隐藏业务编排。并发唯一性、计数和状态转换使用数据库约束或原子操作保证，不只依赖先查询再更新。

用户或外部输入必须校验。可独立调用的业务用例应在可信执行边界检查权限，不能只依赖客户端或某个 HTTP 入口的检查。

日志、异常响应和用户可见结果不暴露凭证、连接信息或不必要的内部实现细节。

## 9. 文档字符串

关键模块、类、函数和方法应写中文文档字符串，解释职责、边界、重要约束和实现原因。清楚的私有小函数可省略，复杂规则、跨模块流程和外部系统封装应写明说明。

单行文档字符串与起止三引号位于同一行，概括文本末尾不加句号：

```python
def normalize_name(name: str) -> str:
    """去除名称首尾空白"""
    return name.strip()
```

多行文档字符串的起始三引号单独成行，正文从下一行开始。参数和返回值等结构化标记采用项目约定的格式，不强行翻译工具术语。

不记录临时任务背景、修改过程或显而易见的实现细节。完整说明使用正常标点。

## 10. 验证

当前使用 uv 管理依赖与环境，Ruff 作为开发依赖提供代码检查和格式化。安装环境及检查命令如下：

```bash
uv sync --locked
uv run ruff check .
uv run ruff format --check .
```

需要格式化时执行 `uv run ruff format .`；可修复问题可使用 `uv run ruff check --fix .`，修复后检查 diff。

开发依赖包含 Ruff、pytest、pytest-asyncio 和 Pyright。Ruff 使用默认检查和格式化行为，不替代类型检查或行为测试；类型检查使用 `uv run pyright`，测试使用 `uv run pytest`，异步测试由 pytest-asyncio 支持。Pyright 使用项目 `.venv`、Python 3.14 和 `src/` 搜索路径；pytest 从 `tests/` 收集测试，并将 `src/` 加入导入路径，具体配置见 `pyproject.toml`。

按实际项目配置运行格式化、静态检查和相关测试。类型检查与运行时行为验证各有用途，不以其中一种代替另一种。

异步、数据访问和接口变更应根据影响验证失败、超时、资源释放、事务回滚或权限边界。只验证本次相关行为，不为追求检查数量重复运行无关测试。

尚未配置工具时，不编造检查命令或通过结果；必要检查无法执行时，在交付说明中写明原因。
